# Прототип охраны и бюджетных наград

Версия 0.2.2. Явная привязка сундука к одному охраннику PoV и отдельная бюджетная добавка EpicLoot.
Генератор комнат ещё не подключён; основной профиль и существующие миры не изменяются.
[Серверный этап 0.2.0](../../docs/reports/2026-10-28-dungeon-budget-rewards.md).
[Клиентский этап 0.2.1](../../docs/reports/2026-10-28-dungeon-client-rewards.md).
[Машинная сводка и SHA256](../../manifests/dungeon-client-reward-results-20261028.json).

## Контракт механизма

- Только PoV 5.3.6 и EpicLoot 0.15.3: версия и SHA256 DLL сверяются с
  [закреплённой поставкой](../../manifests/dungeon-prototype.lock.json). Зависимости не обновляются.
- Мост `PovBridge` сохраняет управляемый набор при синхронизации PoV. Обычные существа не перехватываются.
  `AssignIds` задаёт явный набор; `Bind` читает фактические идентификаторы через PoV `IdOf`, а не их число.
- `GuardedChestReward.Bind(chest, guard, context)` вызывается будущим адаптером комнаты после спавна охраны.
  Оба ZDO должны принадлежать вызывающей стороне. Контекст содержит идентификаторы данжа/комнаты,
  кратчайшую глубину, seed, признак ресурсного пути и явную надбавку. Один охранник — один сундук.
  Повторная привязка к той же охране ничего не меняет; другая охрана или второй сундук отвергаются.
- Сохраняются постоянные токены охранника/сундука, исходный ZDO ID для диагностики, prefab, позиция,
  уровень, маска и строковые ID модификаторов,
  бюджет с разложением, полный снимок правил и его SHA256. Перемещение и смерть не участвуют в расчёте.
  Открытие при живой охране разрешено. Надбавка по умолчанию 0; ресурсный путь требует пустого набора и даёт 0.
- Глобальная таблица — [dungeon-rewards.json](../../configs/dungeon-rewards.json), копируемая в
  `BepInEx/config/dungeon-rewards.json`. Веса и сочетания едины для всех источников; неизвестный ID отвергается.
  Это предварительная калибровка десяти явно перечисленных модификаторов, а не поддержка всех 26 свойств PoV.
- Полная шкала сохраняет Ancient-группу. Следующая шкала имеет ту же длину и размер группы на единицу больше.
  Бюджет не делится на число вещей. Одна редкость на группу, отдельная генерация каждой вещи.
  Нулевой остаток пуст; положительный остаток ниже первого порога даёт 50 монет один раз.
  Множителей ресурсов/игроков у этой добавки нет.
- Основы выбираются из актуальной таблицы prefab сундука EpicLoot, уровень источника 1.
  При нескольких таблицах выбирается таблица равновероятно, внутри неё — штатные веса и ссылки.
  Штатный resolver учитывает масштабирование ссылок; неэкипируемые строки отбрасываются с повтором.
  `Drops`, шанс пустой добычи, глобальные 0,7, удача и Prosperity не отменяют нашу группу.
- Технология — `BossKillUnlocksCurrentBiomeItems`. В закреплённой DLL общий фильтр преждевременно
  отказывает без `Player.m_localPlayer`. Только внутри нашего синхронного выбора узкий Harmony-prefix
  направляет его к штатному `CheckGateBossKill`. Вне этого участка поведение EpicLoot не меняется.
- Ключи мира считываются при первом формировании. Весь набор сериализуется до первого добавления.
  Предметы, качество, seed и ключи сохраняются; новый босс, открытие и перезапуск их не пересоздают.
  Отдельное состояние Unity RNG восстанавливается после генерации и сериализации.
- Полные совпадения основы, качества, варианта и магических свойств в группе отбрасываются.
  Лимиты: 256 попыток выбора основы, 64 попытки уникальности на предмет, 256 предметов в наборе по умолчанию.
  Неподдержанный пул сохраняет ошибку до выдачи всей добавки; обычные предметы остаются доступны.
  Изменение профиля не пересоздаёт такой сундук автоматически.
- Обычный лут, отложенный штатный бросок EpicLoot и награды PoV сохраняются. Отложенный бросок завершается
  его же `TryRoll` при доступном локальном игроке; на сервере pending-флаг остаётся для клиента.
  Повторный полный генератор сундука не вызывается.

## Переполнение и сохранение

Готовые вещи остаются в ZDO-очереди. Добавление сначала проверяется на копии inventory, поскольку
`Inventory.AddItem` может частично добавить монеты и вернуть `false`. Отказ не меняет живой инвентарь.
Одна успешная вставка сохраняет журнал со снимками «до/после» и следующим курсором, затем inventory,
затем завершает журнал. После прерывания точное совпадение со снимком позволяет завершить вставку один раз.
Неизвестное содержимое при незавершённом журнале вызывает диагностический отказ, без его перезаписи.
Журнал сравнивает исходные байты ZDO: повторный vanilla Save/Load не точен для прочности из-за `float`.
Обычные вещи копируются через `Clone`, без повторной загрузки всего inventory на каждую вставку.

Первая генерация запускается через `RPC_RequestOpen`/`RPC_RequestTakeAll` на текущем владельце.
Хук `GetInventory` обслуживает только уже сформированные награды: фоновый скан не открывает новую группу.
`CheckForChanges` продолжает уже сформированную очередь после освобождения места и закрытия сундука.
Под открытым интерфейсом предметы не заменяются. Владелец не захватывается механизмом выдачи.
Во время `Container.Load` выдача также запрещена: клиентские уведомления о добавлении очередной вещи
могут повторно вызвать `GetInventory`, когда инвентарь заполнен лишь частично.
Регрессия `reentrant_load` в ProbeSuite проверяет промежуточные стадии загрузки и одну последующую вставку.
Native ZDO ID перенумеровывается при загрузке мира 1.0.20; связи используют собственные сохраняемые токены.
Схема награды — 2. Одноразовые fixture-сундуки прежней схемы не мигрируются автоматически.
Для смены владельца мод с теми же зависимостями должен быть установлен на клиентах; два клиента ещё нужны
для приёмки. Сундуки `m_autoDestroyEmpty` не поддерживаются. Разрушение сундука с очередью пока не проверено.

## Сборка и автоматические проверки

Нужны .NET SDK 8.0.408 и проверенная поставка Valheim `l-1.0.20`, BepInEx 5.4.2351 с PoV/EpicLoot.
В `GameDir` должны находиться `valheim_server_Data/Managed`, `BepInEx/core` и закреплённые плагины.
Сторонние DLL не входят в Git и не копируются в результат сборки.

```bash
dotnet build tools/dungeon-depth-prototype/DungeonDepthPrototype.csproj \
  -c Release -o .local/dungeon-rewards/build -p:GameDir="$PWD/.local/dungeon-prototype/server"
dotnet run --project tools/dungeon-depth-check/DungeonDepthCheck.csproj -c Release
python3 scripts/forecast-dungeon-rewards.py --runtime-rules configs/dungeon-rewards.json \
  --output .local/dungeon-rewards/forecast.json
make check
```

При приватном SDK использовать его `dotnet` и `DOTNET_ROOT`. Проверки математики не требуют Unity.
Старый прогноз без `--runtime-rules` остаётся историческим примером 10/100, а не конфигом плагина.

## Отдельный серверный прогон

Следовать [runbook](../../docs/runbook.md). Проверить ресурсы/порты, скопировать закреплённую поставку
в новый каталог и сверить SHA256. Не копировать состояние прежних миров, bounty-ledger и старый checkpoint.
Скопировать новую DLL в `BepInEx/plugins/DungeonDepthPrototype` и таблицу в `BepInEx/config`.
Плагин выключен по умолчанию. Для одноразового мира `DungeonRewards`:

```ini
[Runtime]
Enabled = true
ExpectedWorld = DungeonRewards

[Probe]
Enabled = true
Phase = create
```

Запускать `scripts/start-dev.sh` с отдельными `VALHEIM_SERVER_DIR`, `VALHEIM_STATE_DIR`,
`VALHEIM_PASSWORD_FILE`, `VALHEIM_WORLD_NAME=DungeonRewards`, свободным портом и уникальным unit.
Лимиты испытаний: 4 ГиБ RAM, 200% CPU, 900 секунд. Загрузки latest при старте нет.

`create` выполняет реальные вызовы PoV, EpicLoot, Container и Inventory, серии технологических выборов,
сохранение обычного содержимого, проверку пустого/непустого штатного дропа, границ и журнала.
Три fixture-сундука и их охрана остаются в отдельном мире: готовая награда, частично выданная, не сформированная.
Результат: `BepInEx/config/DungeonDepthPrototype/rewards-create.json` и маркер `DUNGEON_REWARDS_PASS`.
Сверять UTC и маркер именно текущего процесса; старый файл не подтверждает новый запуск.

После штатной остановки и `World save (5/5) done` сделать согласованную копию всего состояния,
конфигов и внешних данных модов. Сменить только `Phase = resume`, запустить ту же DLL и тот же тестовый мир.
Проверяются точные сохранённые inventory/награды, новый ключ босса, первая генерация отложенного набора
и завершение очереди. После ещё одной остановки сохранить согласованный backup, восстановить его в отдельный
каталог, сверить SHA256 файлов и запустить ту же поставку с `Phase = verify` для повторной загрузки результата.
Checkpoint содержит приватные ZDO и содержимое сундуков, остаётся вне Git.

Это серверные проверки настоящих объектов без клиента. Они не подтверждают интерфейс, сетевую передачу
между двумя игроками, бой человека, экономику разборки, проход комнат или готовность полного модпака.

## Отдельная клиентская площадка

Клиент ждёт нужного мира без таймаута пребывания в меню. При выходе снимает свои Harmony-патчи,
а при следующем входе заново подключает механизм. `DUNGEON_REWARDS_READY` означает инициализацию,
не успешную игровую проверку. `Probe.Enabled=false` обязателен на настоящем клиенте.

Для подготовки одноразовой площадки создать отдельные поставки, мир `DungeonClientRewards`
и локального персонажа `RewardQA`; основной профиль не подменять. На обеих сторонах:

```ini
[Runtime]
Enabled = true
ExpectedWorld = DungeonClientRewards
[Probe]
Enabled = false
[ClientFixture]
Enabled = true
```

Fixture выключена по умолчанию и работает только в этом мире. Запросы передаются атомарной заменой
приватного `BepInEx/config/DungeonClientFixture/request.json`: `id` — уникальный буквенно-цифровой ID,
`action` — действие, `chest` — имя сундука при позиционировании. Ответ сохраняется как `<id>.json`.

- Серверное `create` один раз создаёт платформу, пять сундуков и живую охрану с отключённым AI.
  Сундуки: `zero`, `coins`, `single`, `groups`, `overflow`; бюджеты 0, 1, 120, 240, 432.
  В 0.2.2 схема `layout 2`: подставки поднимают сундуки на 1,5 м относительно прежнего положения.
- Клиентское `position` перемещает только `RewardQA` к выбранному сундуку и включает god/ghost.
  Взгляд горизонтальный; команда отклоняет прежнюю схему площадки, не перемещая старые сундуки.
  `teleport_started` подтверждает только начало. `position-status` с тем же `chest` читает
  `ready_to_open`: телепортация закончена и под прицелом именно нужный Container. Контейнер не открывается.
  Это подготовка, а не проверка доступности площадки обычному персонажу.
- `prepare-overflow` завершает штатный pending EpicLoot и заполняет свободные ячейки древесиной
  только у владельца ещё не сформированной награды. `fill-player`/`clear-player-filler` управляют
  отдельно помеченным наполнителем персонажа. Эти действия требуют закрытого интерфейса инвентаря.
- `snapshot` читает сундуки, персонажа, очередь, свойства вещей, ключи мира и живую охрану.
  `events.jsonl` фиксирует владельца/local UID, использование, курсор, журнал, ошибку и хеш inventory.
  Сервер дополнительно читает ZDO выгруженных сундуков; UID в данных не доказывает наличие загруженного Container.
  Сырые ответы и события содержат приватные идентификаторы и остаются вне Git.

Открытие, выбор вещи и «Забрать всё» выполняются только через игровой интерфейс по
[визуальному протоколу](../../docs/visual-testing.md). После завершения и backup отключить fixture и runtime.
Backup должен объединять мир, персонажа и внешние данные модов после штатной остановки обеих сторон.
Откат только мира при сохранении продвинувшегося персонажа не является согласованным восстановлением.
Для продолжения этой площадки восстановить также её тестовые конфиги: fixture удерживает платформу
от разрушения и отключает AI охраны. Не загружать её как обычный игровой мир с выключенной подготовкой.
Checkpoint прежней площадки продолжать с сохранённой DLL 0.2.1; геометрия не мигрируется.
Новую схему проверять на отдельном новом состоянии после согласованного backup.
Высота и фокус новой схемы проверены одним настоящим клиентом: пять сундуков открыты через `E` без наклона
до и после перезапуска, содержимое и позиции сохранены. Проверенный профиль — 1280×720/DPI 96/English.
Другие настройки камеры и интерфейса требуют калибровки.
