# Приватный инструмент анализа боя

Инструмент предназначен для оператора испытаний. Игровой интерфейс и сообщения персонажу не добавляются.
Журналы содержат имена, позиции и игровые идентификаторы: хранить их только в `.local/` или вне checkout.

## Разбор прежней попытки

`scripts/analyze-combat.py` читает серверные `ForestManual/*/events.jsonl`, отбирает персонажа,
проверяет пропуски/повторы и разделяет входы. Повторное падение к 1 HP после лечения не считается новой попыткой.
Позицию последнего события можно сопоставить со снимком `ForestCryptQA/snapshot` и исходным снимком.

```bash
python3 scripts/analyze-combat.py --events .local/attempt/events.jsonl \
  --snapshot .local/attempt/after.json --baseline .local/attempt/before.json \
  --player Drug --output .local/attempt/analysis.json
```

Результат — JSON: источники событий, время первой условной смерти, пропуски последовательности,
ближайшая охрана по исходным комнатам/глубинам/числу свойств и отдельно арена. Времена — UTC.
Радиус сравнения по умолчанию 5 м в трёх измерениях. Позиция после боя не доказывает авторство каждого удара.
Вывод в публичный каталог checkout запрещён; файл создаётся с правами `0600`.

## Подробная запись кандидата 0.7.0

В отдельной поставке включить `[CombatAnalysis] Enabled = true` в конфиге собственного плагина.
Пример — [профиль кандидата](../configs/forest-gated-candidate.cfg).
Сборщик пишет `BepInEx/config/CombatAnalysis/<UTC>-<stream>.jsonl` на каждом запущенном экземпляре игры.
Нужны журналы клиента и сервера: обработку урона выполняет владелец сетевого объекта.
При двух клиентах могут понадобиться оба клиентских журнала. Отсутствующий журнал не означает нулевой урон.
Автоматическая передача этих файлов на сервер пока не реализована.

Записываются:

- `damage_rpc`: конкретные атакующий и цель, prefab, звёздный уровень, свойства, исходная комната,
  позиции, HP/щит до и после обработки, компоненты удара на входе и выходе наблюдаемого обработчика;
- `health_damage`: вложенный этап `ApplyDamage` с ID внешнего события, чтобы не складывать один урон дважды;
- `healing`: сумма фактического восстановления и число вызовов за интервал, отдельно внутри и вне обработки удара;
- `nearby`: раз в секунду ближайшие участники в радиусе 35 м, максимум 128 с явным числом пропущенных;
- состояние god/ghost, доля выносливости, текущее оружие, его качество и прочность;
- начало/завершение потока, последовательность событий и достижение лимита файла.

Новая охрана получает постоянный диагностический ID при создании. Старые существа и игроки используются
с нативным ID, ограниченным потоком записи: такие строки нельзя молча склеивать между перезапусками.
Запись не создаёт щит, не меняет здоровье или настройки противника и не перехватывает сетевое владение.
Лечение агрегируется; буфер сбрасывается раз в секунду. Лимит — 64 MiB на поток;
его достижение останавливает запись с отметкой неполноты, не удаляя прежние данные.
При аварийном выходе возможна потеря последнего буфера. Незавершённый файл и оборванная последняя строка
отмечаются анализатором, повреждение середины и конфликтующие повторы приводят к отказу.

```bash
python3 scripts/analyze-combat.py --combat .local/attempt/client.jsonl .local/attempt/server.jsonl \
  --player Drug --output .local/attempt/detailed-analysis.json
```

Сводка разделяет входящий/исходящий урон, HP и щит, восстановление по существам и максимальное наблюдаемое
скопление в радиусе 5 м. Вложенный `health_damage` не прибавляется повторно к итогам `damage_rpc`.
Входной пакет, прошедший обработку пакет и изменение HP — разные показатели.
Сумма потери HP при god не является полным уроном. Нулевой результат RPC может означать уклонение,
блокировку или иное условие обработки, а не неуязвимость.

Текущее оружие в момент получения урона может отличаться от оружия, выпустившего снаряд.
Контекст лечения внутри RPC помогает локализовать `Greedy`, но сам по себе не доказывает источник лечения.
Снимок чужого объекта может содержать сетевую задержку; в записи отмечается локальное владение.
Состав еды, полный набор зачарований и дерево навыков пока нужно фиксировать отдельным снимком условий.

## Проверка

`combat-analysis-probe` через приватный интерфейс `ForestCryptQA` выполняет парные удары по свежим
скелетам без свойств, со щитом и с десятью свойствами: сначала без записи, затем с записью.
Результаты HP/щита должны совпасть. Проба создаёт и удаляет только собственных временных существ;
использовать её на отдельном QA-сервере. Она не подменяет клиентский бой и проверку передачи владения.
