# Подготовка и проверка поставки

## Локальные данные

Использовать Linux x86-64, Python 3.11+, curl, unzip, tar, OpenSSH и пользовательский systemd.
Для SteamCMD нужны 32-битные библиотеки; для сервера — библиотеки из
[официального руководства](https://www.valheimgame.com/support/a-guide-to-dedicated-servers/).
Выполнять из корня checkout. Все примеры предполагают отдельный тестовый мир.

```bash
mkdir -p .local/evidence .local/downloads .local/steamcmd
chmod 700 .local
sudo apt-get install --no-install-recommends lib32gcc-s1 lib32stdc++6 libatomic1 libpulse0 libpulse-dev
```

SSH-доступы хранить в `~/.ssh/config`, например под алиасами `valheim-client` и `valheim-server`.
Пароли и ключи не переносить в checkout. На Windows для администратора используется
`%ProgramData%/ssh/administrators_authorized_keys` с ACL для SYSTEM и Administrators:
[инструкция Microsoft](https://learn.microsoft.com/en-us/windows-server/administration/openssh/openssh_keymanagement).
Существующие ключи сохранять. Проверять доступ отдельным соединением с `BatchMode=yes`.

Сборщик инвентаризации только читает клиент. Результат может содержать идентификаторы Steam и приватные
настройки, поэтому не публикуется. Исходный modded-клиент для новой конфигурации больше не требуется.

```bash
python3 scripts/collect-client.py --host valheim-client --output .local/evidence/client-new.json
```

## Получение игры и модов

SteamCMD загружать с официального адреса, фиксировать SHA256 bootstrap-архива локально:

```bash
curl -fL -o .local/downloads/steamcmd_linux.tar.gz https://steamcdn-a.akamaihd.net/client/installer/steamcmd_linux.tar.gz
sha256sum .local/downloads/steamcmd_linux.tar.gz
tar -xzf .local/downloads/steamcmd_linux.tar.gz -C .local/steamcmd
bash scripts/install-server.sh .local/steamcmd/steamcmd.sh .local/server-new
```

Установщик требует новый каталог. SteamCMD получает текущую public-ветку, а не исторический build по номеру.
После скачивания сверить `steamapps/appmanifest_896660.acf` с `manifests/server-build.json`;
другая версия — новый кандидат и новый цикл испытаний. Номер build клиента и сервера может различаться:
это разные приложения Steam. Сверять также версию игры и сетевой протокол.

```bash
python3 scripts/fetch-packages.py --lock manifests/core-candidate.lock.json
python3 scripts/stage-foundation.py --output .local/foundation-new
python3 scripts/stage-foundation.py --profile core --output .local/core-new
python3 scripts/stage-foundation.py --profile core --target client --output .local/core-client-new
```

При наличии lock загрузчик проверяет архивы, основные DLL и зависимости по его значениям.
Исходная инвентаризация нужна только для первого восстановления присланных версий.
Никакие недостающие зависимости автоматически не выбираются. Для нового состава создаётся отдельный lock.
Совпадение DLL не подтверждает настройки и игровую совместимость.

Для разрешённого обновления сначала проверить страницы авторов и указать точные версии в новой выборке.
Поле `representative_files` сопоставляет каждому полному имени пакета имя его основной DLL.
Затем закрепить скачанные архивы:

```bash
python3 scripts/fetch-packages.py --selection manifests/core-update-20261028.json --lock manifests/core-update-20261028.lock.json --observe-releases
```

В новом lock `verification_source = release-archive-observation` означает хеш скачанного релиза,
а не совпадение с прежней пользовательской инвентаризацией. Повторный вызов проверяет существующий lock.
Сборщику overlay передавать ту же выборку через `--selection` и тот же lock через `--lock`.
Он включает новые пакеты и версии независимо от старой инвентаризации.

Overlay создаётся только в новом каталоге. Для runtime копировать чистую установку игры в отдельный каталог,
затем накладывать нужный overlay. Не копировать поверх работающего процесса или прежнего постоянного мира.
Исходные архивы с лицензиями сохраняются локально. Общие инструкции BepInEx:
[публикация сопровождающих пакет](https://thunderstore.io/c/valheim/p/denikson/BepInExPack_Valheim/).

Серверный профиль исключает PlantEasily и его конфиг; клиентский сохраняет их. Для core накладываются
согласованные настройки из `configs/core`: Bloodgill выключен, опора Forever Build 2 ×3, EpicLoot 0,7,
TidyChests 15 м без изучения рецептов, выбранные параметры рюкзаков и растений.
При запуске BepInEx дополняет файлы параметрами новой версии. Сравнивать результат миграции с исходным профилем.
Не заменять ими уже настроенный runtime без сравнения изменений.

## Запуск стенда

Создать приватный файл пароля с правами `0600`, минимум пять символов. Не выводить его в отчёт.
Переменные ниже являются параметрами запуска, а не командами установки.

```bash
export VALHEIM_SERVER_DIR="$PWD/.local/server-new"
export VALHEIM_STATE_DIR="$PWD/.local/state-new"
export VALHEIM_PASSWORD_FILE="$PWD/.local/server-password"
export VALHEIM_WORLD_NAME=Development
export VALHEIM_MODE=vanilla
export VALHEIM_UNIT=valheim-dev
bash scripts/start-dev.sh
```

После добавления overlay использовать `VALHEIM_MODE=bepinex`. Игра запускается с обычной добычей ×3
(`-modifier resources most`), Steam backend и `-public 0`. Это скрывает сервер из списка,
но не является сетевым firewall. Используются UDP 2456–2457; crossplay для локальной проверки не включён.
`start-dev.sh` ограничивает процесс 4 ГиБ памяти, 200% CPU и десятью минутами работы.
Лимиты меняются через `VALHEIM_MEMORY_MAX`, `VALHEIM_CPU_QUOTA`, `VALHEIM_RUNTIME_MAX`; для ручного длительного
теста допустимо `VALHEIM_RUNTIME_MAX=infinity` после проверки ресурсов. Нагрузочную ёмкость это не доказывает.

```bash
systemctl --user show valheim-dev -p ActiveState -p MemoryPeak -p CPUUsageNSec
systemctl --user stop valheim-dev
```

Остановка передаёт SIGINT игре, затем ждёт до 120 секунд. Сервис временный: для нового запуска снова вызвать
`start-dev.sh`. Журналы — в каталоге состояния и `BepInEx/LogOutput.log`. Скопировать их в приватный отчёт
до следующего старта. `Game server connected` подтверждает запуск, а не подключение реального игрока.

## Backup, перезапуск и восстановление

После штатной остановки убедиться в завершённом `World save (5/5) done`, отсутствии процесса и свободных
портах. Скопировать **весь каталог состояния** и все внешние данные модов. Формат 1.0.20 включает каталоги
миров с `.db2`, `.fwl2`, `.chunk`, `.chunks`, `.ok`; копии только старых `.db/.fwl` недостаточно.

```bash
mkdir -p .local/backups
tar -czf .local/backups/state-new.tar.gz -C .local state-new
sha256sum .local/backups/state-new.tar.gz
```

Для нового backup использовать уникальное имя. Проверка восстановления: распаковать в отдельный каталог,
запустить **ту же поставку** с новым `VALHEIM_STATE_DIR`, дождаться подключения сервера и загрузки мира,
проверить объекты и награды реальными клиентами. Сохранять backup до проверки, не восстанавливать поверх
работающего сервера. Откат версии модов может требовать одновременно отката мира и внешних данных модов.

### Ограничение количества копий

Для каждого тестового мира и персонажа держать 4 игровые автокопии и до 5 полных согласованных копий.
Вместе с одной служебной предыдущей версией `.old` это бюджет до 10 точек восстановления.
В клиенте используется `AutoBackups = 4`, в серверном запуске уже задано `-backups 4`.
Этот параметр управляет только игровыми автокопиями; ручные архивы он не удаляет.
Описание серверного параметра — в
[руководстве Iron Gate](https://www.valheimgame.com/support/a-guide-to-dedicated-servers/).

После создания и проверки очередной полной копии сверять количество и удалять самые старые сверх 5.
Последняя проверенная восстановлением копия и копия перед текущим изменением входят в эти пять;
их не удалять до появления проверенной замены. При необходимости сначала проверить восстановление новой копии.
Учитывать также ручные копии в Manage saves, миграционные backup и временные каталоги восстановления:
они не ограничиваются `AutoBackups`. Клиентские архивы ротирует скрипт запуска;
серверные checkpoint пока ротируются оператором после проверки.
Не удалять отдельные `.chunk`, `.ok` и другие части мира ради уменьшения счётчика файлов.

Поставку с игровыми бинарниками и модами хранить отдельно и ссылаться на её manifest из backup состояния.
Не включать её заново в каждый архив сохранений. Снимок состояния по-прежнему должен включать весь каталог
мира, фактические файлы персонажа, настройки и внешние данные модов после остановки всех писателей.

## Перенос на целевую машину

До переноса завершить [игровую приёмку](design.md#игровая-приёмка), закрепить конфиги и разделение
client/server. Подготовить полный manifest файлов поставки с SHA256 и архив с контрольной суммой;
`server-build.json` содержит только идентичность build и несколько контрольных файлов, этого для релиза мало.

План размещения: `/srv/valheim/releases/<release-id>` для поставок, отдельные `state`, `backups` и `secrets`.
Runtime изолировать Docker-контейнером с явными лимитами ресурсов и штатной остановкой SIGINT.
Начальные 16 ГиБ на целевой машине — бюджет для оценки, не подтверждённая потребность.
Контейнерную поставку ещё нужно реализовать и проверить; локальный стенд использует systemd напрямую.

Переносить проверенный архив, сверять полный SHA256, иметь предыдущую поставку и согласованный backup.
Не выполнять обновления Steam/модов при старте и не использовать `git pull` для замены файлов работающего
сервера. До переключения проверять порты, свободную память, диск и влияние соседних служб.
Внешняя доступность и проброс на маршрутизаторе проверяются отдельно от LAN-доступа.

## Проверка инструментов

### Автоматические игровые сценарии и подключение к серверу

Проверять на отдельной копии Windows-клиента с тем же закреплённым overlay. Перед копированием
проверить диск/RAM и отсутствие процесса игры. Сохранить одну исходную копию `HKCU\Software\IronGate\Valheim`;
параметры Unity общие для пользователя Windows даже при отдельном каталоге игры. Пользователь разрешил
оставлять тестовые настройки постоянно: после теста их больше не восстанавливать автоматически.
В тестовой копии отключить только консольное окно BepInEx, чтобы оно не перехватывало foreground.
Запускать в интерактивной сессии через постоянный ярлык `Valheim Test` или
[скрипт запуска](../scripts/windows/start-client-test.ps1). Он использует окно 1280×720 и собственный `-logFile`.
Клиентский `-savedir` убран: в этой сборке он не задаёт расположение персонажей.
Постоянные пути, backup и очистка описаны в [runbook стенда](test-stand.md).

Профиль для данного стенда закреплён в [client-test.json](../configs/client-test.json): окно 1280×720,
отрисовка в родном разрешении окна, лимит 60 FPS, VSync выключен, Custom на основе Medium.
Детализация High, растительность/свет/тени Medium, 15 активных источников света и одна точечная тень,
SSAO Low, дальность Classic; размытие движения, глубина резкости, bloom и хроматические аберрации выключены.
Масштаб интерфейса — 100%, язык сценариев — English. Это профиль функциональных тестов,
а не измерение максимальной производительности при 1920×1080.

При закрытой игре применить профиль из PowerShell в учётной записи тестового клиента:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts/windows/set-client-test-settings.ps1 `
  -ProfileJson configs/client-test.json -TestClientDirectory $testClient `
  -SettingsBackupDirectory $settingsBackup
```

`$testClient` должен указывать на отдельную тестовую копию, `$settingsBackup` — на приватный каталог вне Git.
Скрипт сохраняет одну исходную копию настроек, включает кэш BepInEx, отключает отдельное консольное окно
и повторную запись Unity-сообщений в `LogOutput.log`. Полный Unity-журнал остаётся в собственном `-logFile`,
журнал модов и сообщения об ошибках сохраняются. Не очищать кэш при каждом старте и не отключать журналы ошибок.
Профиль проверен для 1.0.20; после смены версии снова проверить значения через интерфейс и повторный запуск.

В Gameplay включить `Skip intro cinematic`; профиль также сохраняет эту настройку.
В окне AdventureBackpacks снять `Show on Game Startup` (`Local Config / Show Splash on Startup = false`).
Остальные обучающие диалоги и вступление нового персонажа — отдельные состояния, этот переключатель их не отменяет.
Штатная панель F2 в игровом мире содержит FPS и сетевую диагностику: сторонний мод для счётчика не нужен.
Для замеров максимального FPS временно снять лимит, записать условия и затем вернуть 60;
измерения меню и мира не смешивать. Панель F2 закрывать перед сценариями, которым она перекрывает интерфейс.

Создать отдельного персонажа и через Manage saves перевести его в Local save. Сам по себе `-savedir`
не отключает Cloud save и не доказывает смену каталога локальных персонажей. Проверить фактические файлы:
в испытанном клиенте 1.0.20 они оказались в стандартном `characters_local`, а переданный каталог был пустым.
Этот компьютер целиком выделен под испытания: текущая учётная запись Windows и стандартный каталог
сохранений являются постоянным тестовым профилем. Дополнительная учётная запись не нужна.
После разового возврата тестового персонажа не переносить его между папками при каждом запуске.
Первые диалоги модов и вступление пройти с визуальной проверкой каждого состояния.
Записать фактический build клиента, SHA256 DLL/конфигов
и идентичность работающего окна. Подготовить приватный профиль сценария согласно протоколу ниже.

Сервер запускать на новом мире с лимитами CPU/RAM. До входа убедиться в готовности и совпадении версий.
В Favorite добавить только адрес тестового сервера; не считать отсутствие ответа A2S доказательством
недоступности игрового соединения. После первого входа проверить управление и инвентарь.

Повторяемые сценарии и формат профиля описаны в [протоколе](visual-testing.md#сценарии-с-ocr).
После сохранения и выхода остановить сервер, сделать полный backup состояния и внешних данных модов,
восстановить в новый каталог, сверить SHA256 и повторить вход тем же клиентом. Проверять инвентарь
и положение персонажа отдельно от сохранности построек, сундуков и наград.

По окончании штатно закрыть тестовый клиент и сохранить его локальные данные; профиль экрана оставить.
Сверить файлы персонажа в backup, а не только наличие каталога `-savedir`.
Остановить тестовые серверы и проверить оставшиеся задания `ValheimVision-*`.

### Локальные проверки кода

Для наблюдения игрового окна и приёмки через интерфейс использовать
[протокол визуального тестирования](visual-testing.md). Он разрешает программный ввод
и описывает получение кадров из интерактивной сессии Windows через SSH.

```bash
make check
```

Это проверки архивов, передачи кадров, ограничений ввода, остановки сценариев, Python-синтаксиса,
shellcheck и whitespace.
Они не заменяют игровые тесты.
