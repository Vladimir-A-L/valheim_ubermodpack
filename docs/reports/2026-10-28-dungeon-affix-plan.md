# Собственный мод: глубина, модификаторы PoV и награды EpicLoot

Дата: 28 октября 2026 года, Asia/Yekaterinburg.
Основание: уточнение пользователя после [плана генерации](2026-10-28-dungeon-generation-plan.md)
и ответ «Общая добыча × число участников».
Статус: проектирование и статическая проверка DLL. Собственный мод ещё не создан, игровые испытания не проведены.

Последующее уточнение отменило множитель добычи по числу участников и переработку генератора добычи PoV.
Десять модификаторов и Ancient больше не задают обязательный порог.
Актуальные расчёты и проверка технического прототипа — в [новом отчёте](2026-10-28-dungeon-prototype.md).
Ниже сохранён предыдущий вариант плана; его ограничения количества не являются действующими правилами.

## Выбранное поведение

- Собственный мод управляет геометрией, глубиной, назначением модификаторов и наградами.
  Max Dungeon Rooms остаётся изученным примером, его установка/доработка исключена из текущего пути.
  DungeonMaps сохраняется кандидатом навигации; Crypts and Caverns — дополнительных ранних данжей.
  OdinsHollow отложен. CLLC исключён; PoV остаётся системой дерева и сложности противников.
- Цепочка: путь от входа → диапазон глубины → число модификаторов PoV → вероятности редкости EpicLoot.
  Глубину считать по графу проходимых соединений. Соседние параллельные ветки не должны становиться
  разными ступенями лишь из-за порядка их генерации. Профиль фиксируется вместе с данжем.
- Вход и первая ступень: 0 модификаторов; вторая и третья: 1; далее аналогично.
  Предложение для прототипа — `modifierCount = floor(depthStep / 2)`.
  Если ступень равна одному переходу между комнатами, 10 модификаторов начинаются с 20 переходов.
  Это пример шкалы, не обещание подходящей геометрии и баланса для каждого типа подземелья.
- Учитывать общее число назначенных модификаторов. Штатный случайный набор PoV не должен добавляться
  поверх цели, иначе даже вход не будет иметь согласованные 0. Дополнительный множитель HP/урона не вводить.
  Не использовать повышение звёзд как обход ограничения API назначения модификаторов.
- Выманивание и другие тактические способы облегчить бой разрешены. Награда существа определяется
  сохранённым профилем его появления; перемещение к выходу её не меняет. У сундука собственный профиль комнаты,
  который не зависит от ближайшего живого врага. Обязательная зачистка для открытия не предусмотрена.
- На пороге 10 модификаторов допускается ненулевой шанс Ancient, красной редкости EpicLoot,
  в сундуках даже Тёмного леса. Конкретный процент пока не выбран. Редкость и технология предмета разделены:
  базовые предметы/обычные ресурсы остаются в рамках этапа данжа, высокая редкость разрешена раньше.
- Глубина меняет распределение редкости, количество наград остаётся независимым от неё.
  Общая добыча умножается на число участников; это собственное правило, выбранное пользователем.
  Доступные первые ресурсы прогрессии, питание своего этапа и облегчённый проход с железом сохраняются.

## Что фактически проверено

PoV 5.3.6 скачан из опубликованного архива только для чтения; в игровые профили не установлен.
SHA256, размер и зависимости записаны в
[manifest исследования](../../manifests/dungeon-affix-review-20261028.json).
Объявлены `denikson-BepInExPack_Valheim-5.4.2333` и `ValheimModding-Jotunn-2.30.2`.
Это зависимости архива, не основание понижать закреплённый загрузчик 5.4.2351.
Будущая установка требует отдельного lock с фактически выбранными версиями и проверки совместимости.

Дополнительно прочитаны API установленного EpicLoot 0.15.3, его локальные базовые JSON
и `CharacterDrop`/`Container` сервера Valheim `l-1.0.20`, build `25909431`.
Архивы, DLL, декомпилированный код и исходные наблюдения с UTC-временем находятся только в `.local/`.
В публичные файлы внесены собственное описание результатов, ссылки и хеши.

### PoV: техническая основа есть, поддерживаемого setter нет

В [публичном API PoV](https://valheiman.com/api) доступны чтение параметров существ и исключение prefab
из обработки через `LeaveAlone`. Назначение набора модификаторов конкретному существу не предоставлено.
Это подтверждено чтением `Valheiman.Api.Creatures` в DLL 5.3.6. Автор гарантирует контракт только
для `Valheiman.Api`; внутренние классы могут меняться без сохранения совместимости.

Внутренний `PassiveTree.RarityMods` содержит 26 разных флагов, методы `Fill` и `Set`.
`Set` записывает набор в ZDO существа, требует владения объектом и может пытаться его получить.
`Fill` выбирает доступные модификаторы, учитывает запреты и взаимное исключение стихийных вариантов;
при исчерпании пула останавливается раньше запрошенного количества.
Само наличие 26 флагов не доказывает возможность 10 допустимых модификаторов для каждого существа.

`PassiveTree.RarityRoll.Sync` штатно пересчитывает набор через число звёзд и настройку модификаторов на звезду.
Однократного вызова внутреннего setter недостаточно: последующая синхронизация может убрать назначенный набор.
Предпочтительная долгосрочная интеграция — публичная точка назначения по запросу к автору API.
Технический вариант прототипа — изолированный адаптер закреплённой 5.3.6 с явной проверкой версии,
управлением штатным пересчётом только для наших существ и испытанием смены сетевого владельца.
Наличие этого варианта ещё не означает готовую или поддерживаемую интеграцию. Сообщения автору не отправлялись.

### Количество: у PoV есть самостоятельные прибавки

В исследованной DLL default `Reward per modifier` равен 0,5: каждый модификатор добавляет долю
к количеству собственной добычи PoV и опыту. Собственная обычная добыча существа этим параметром не меняется.
Это прочитанное значение по умолчанию, не сгенерированный и испытанный конфиг нашего профиля.
Также найдены отдельные прибавки количества за звёзды, `ItemQuantityPct` и `ChestQuantityPct` из дерева.
На размер награды влияют дополнительные настройки сложности PoV; одной правки таблицы EpicLoot недостаточно.

Поэтому для управляемых данжей нужен единый расчёт количества и явное согласование выдачи трёх источников:
обычных предметов, EpicLoot и PoV. Недостаточно поверх их независимых выдач добавить ещё одну награду.
Глобальное обнуление `Reward per modifier` одновременно затронет опыт и противников вне данжа;
для выбранной задачи следует отдельно обрабатывать количество внутри данжа, сохраняя политику опыта.

В коде игры нет универсального множителя всей добычи по размеру группы:
`CharacterDrop.GenerateDropList` применяет число игроков только к строкам с флагом `m_onePerPlayer`,
а `Container.AddDefaultItems` не умножает весь сундук по общему онлайну.
Такие специальные строки нельзя повторно умножить вместе с уже учтённой группой.

### EpicLoot: редкость можно назначать отдельно

В API DLL 0.15.3 подтверждён `TryMakeMagicItem(item, rarity, luck, legendaryID)`:
он зачаровывает переданный подходящий предмет с указанной редкостью.
Это позволяет выбирать базовый предмет своего этапа отдельно от редкости и количества экземпляров.
Контракт описан в [API EpicLoot](https://github.com/RandyKnapp/ValheimMods/blob/main/EpicLoot/docs/API.md).
Для генерации набора предметов, их размещения, сохранения и однократной выдачи всё равно нужен наш код.

В исследованных `enchantcosts.json` разборка Ancient-оружия даёт `DustAncient` и `EssenceAncient`,
а Ancient-брони/щита — `DustAncient` и `ReagentAncient`. Само действие имеет стоимость и требования;
наличие записи не доказывает доступность разборки сразу при входе в Тёмный лес.
Но ранний Ancient создаёт запас материалов этой редкости для дальнейшего ремесла.
Требуется испытать силу зачарований, доступность разборки, последующее зачарование и перенос эффектов,
если он доступен в выбранной конфигурации. Автоматический запрет этих действий не принят.

## Расчёт награды для прототипа

`Q = Qbase × N`: одиночный объём награды умножается один раз на число участников данного прохождения.
В `Qbase` сохранить обычную основу ×3 там, где она применяется, и исходный шанс EpicLoot с множителем 0,7.
Прибавки количества от глубины, звёзд, модификаторов и характеристик дерева в этом расчёте отсутствуют.
Не умножать ×3 повторно и не выдавать каждому игроку ещё по отдельной копии уже умноженного общего набора.

Для стопок умножается количество, для снаряжения создаётся соответствующее число экземпляров.
Предлагается независимо бросать редкость каждого экземпляра по одной таблице зоны.
Это не гарантирует каждому участнику Ancient и не закрепляет предмет за конкретным получателем.
С ростом `N` увеличивается вероятность увидеть хотя бы один редкий предмет во всей общей добыче;
при неизменном распределении это ожидаемое следствие большего количества экземпляров.

`N` относится к участникам конкретного данжа/столкновения, а не ко всему серверу.
Рабочее предложение: учитывать участие поблизости, включая поддержку, без требования нанести урон лично.
Точные границы, учёт погибших/вернувшихся и позднего присоединения проверить в прототипе.
Зафиксировать `N` при выдаче боевой награды или первом формировании содержимого сундука.
Повторное открытие, переподключение и смена владельца не создают дополнительную выдачу.
Сундук может создавать исходное содержимое до появления игроков: точку формирования награды нужно
согласовать с учётом участников, не домножать уже забранные предметы при следующем открытии.

У существа хранить идентификатор источника, комнату, ступень, фактический исходный набор модификаторов
и версию профиля награды. У сундука — комнату, целевую ступень, версию профиля и состояние выдачи.
Время смерти и расстояние до входа при смерти не заменяют сохранённый профиль.
Если доступный пул не позволяет получить целевые 10 модификаторов, это отказ критерия прототипа;
не объявлять достигнутой эту угрозу на основании одного запрошенного числа.

## Проблемы и предложения

1. **Число модификаторов не равно линейной сложности.** Их сочетания и тип существа могут дать
   непропорционально сильный бой или почти бесполезные эффекты. Сохранить выбранную шкалу количества,
   но испытать совместимые наборы для каждого типа врагов. Начать с 0, 1, 3, 5 и 10; не считать 10
   уже сбалансированным значением для бронзового снаряжения. Проверить читаемость эффектов в узких комнатах.
2. **Модификаторы могут менять состав боя.** Например, `Splitting` делит существо, `Heir` передаёт эффект
   соседу. Проверить сохранение исходного профиля награды, бюджет дочерних существ и поведение пересчёта PoV.
   В прототипе предложено сначала проверить набор без этих двух эффектов, затем рассмотреть их отдельно.
3. **Ранний Ancient меняет силу и ремесло.** Ограничение базового металла полезно, но недостаточно для
   прежнего темпа развития. Сравнить прохождение после такой находки и добычу магических материалов;
   процент Ancient подобрать по этим результатам, не запрещая согласованную возможность.
4. **Глубокий данж всё равно даёт больше добычи за полный проход.** Причина — дополнительные враги/сундуки,
   даже при одинаковом количестве с одного источника. Вместе учитывать MWL ×2, ресурсы ×3 и множитель группы.
   Измерять добычу за время прохождения и за весь данж, отдельно от распределения редкости.
5. **Все типы требуют отдельных профилей.** Геометрия и ограничения генераторов уже описаны в предыдущем
   отчёте. Для готовых интерьеров и чужих генераторов нужны адаптеры; успех одного склепа не закрывает весь охват.

## Приёмка первого прототипа

1. Отдельный мир/профиль: один тип данжа Тёмного леса, сохранённый граф комнат, несколько seed,
   доступные вход/выход и первые ресурсы. Измерить достигнутую глубину, ветвление и стоимость генерации.
2. Назначить существам 0, 1 и 10 допустимых модификаторов независимо от звёзд. Проверить обычную
   синхронизацию PoV, выманивание, выгрузку/загрузку, перезапуск и передачу владельца между двумя клиентами.
   Одинаковые существа на поверхности сохраняют обычное поведение PoV.
3. На фиксированном числе источников проверить одинаковое количество при разных глубинах и одной группе,
   затем общий объём ×2 для двух участников. Проверить сундуки, обычную добычу, EpicLoot и выдачи PoV,
   бонусы дерева, специальные строки `onePerPlayer`, пределы стопок и переполнение инвентаря сундука.
4. Подтвердить распределение редкости на серии выдач: Ancient возможен на выбранном пороге,
   базовые предметы соответствуют технологии, повторный вход не перебрасывает награду.
5. Игровое прохождение: ранний вход за ядрами, обычная и усиленная бронза, железо, разные роли группы.
   Проверить последствия раннего Ancient и бюджет дополнительных существ от модификаторов.
6. Сохранение и восстановление согласованной копии мира/внешних данных; затем расширять матрицу типов.
   Перед запуском проверить ресурсы/порты и установить лимиты процесса согласно runbook.
