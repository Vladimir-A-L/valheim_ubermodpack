# Сокращение клиентских прогонов и оценка MCP

Дата: 30 октября 2026 года, Asia/Yekaterinburg.
Статус: изменены правила и подготовлена задача нового чата. MCP не установлен; игровые прогоны не выполнялись.

## Решение о проверках

Пользователь просит меньше проверок клиентом агента и готов выполнять больше игровых заданий сам.
Основной выигрыш ожидается от изменения процесса: проверки логики, урона и сохранности сначала выполняются
кодом и сервером; агент передаёт готовый кандидат и небольшие группы ручных заданий.
Клиент агента нужен только для конкретной ошибки или неизвестного клиентского поведения.
Новый порядок закреплён в [визуальном протоколе](../visual-testing.md#разделение-проверок-с-пользователем).
Пользовательские задания — в [задаче реализации](../tasks/miniboss-custom-arena.md#ручная-проверка-пользователем).

Это не отмена проверки подключения, отображения и совместной игры: меняется исполнитель.
Результаты сервера, автоматического клиента и наблюдения пользователя записываются раздельно.
Процент ускорения не измерялся; обещания конкретного сокращения времени нет.

## Что уже имеется

`ForestFixture` в тестовом мире читает `request.json`, проверяет ID, переносит запрос в архив
и пишет ответ JSON с временем UTC. В `MiniBossTrial` есть команды состояния, каталога, навигации,
проверки параметров, смерти/награды и двери; создание площадки также выделено в отдельную команду.
Скрипты захвата/ввода и проверки распознаванием уже существуют, как и подготовка/backup/запуск стенда.
Этого достаточно, чтобы выполнять текущую задачу без внедрения MCP.

Текущий интерфейс использует один файл входящего запроса. Нужны сериализация команд и атомарная запись,
иначе одновременные запросы могут конфликтовать. Проверка существующего файла результата защищает лишь часть
повторов: обрыв между изменением мира и записью ответа нельзя считать гарантированно безопасным повтором.

## Где MCP поможет

По официальной документации Codex поддерживает локальный процесс MCP через STDIO и Streamable HTTP;
конкретное подключение зависит от используемого приложения. Веб-интерфейс не читает локальный `config.toml`
так же, как CLI/IDE. Поэтому способ подключения следует выбирать под фактическую среду следующего чата,
а не обещать доступность сервера лишь по наличию его файлов.
[Документация MCP](https://learn.chatgpt.com/docs/extend/mcp?surface=cli).

Наш вывод: полезен небольшой адаптер к существующим командам, прежде всего для получения состояния и кратких
отчётов. Вместо ручного составления JSON, доставки, ожидания файла и фильтрации журнала агент вызывает один
инструмент с явными параметрами. Сборка, геометрия и сама логика испытаний остаются в имеющемся коде.
MCP не создаёт эти возможности автоматически и не сокращает загрузку Valheim, Steam или время боя.

Возможный первый набор инструментов, **ещё не реализованный**:

| Инструмент | Назначение |
| --- | --- |
| `qa_status` | Версия кандидата, готовность сервера, краткое состояние встречи и наличие подключённых игроков |
| `qa_inspect_encounter` | Режим босса, HP/щит, цель, зона, преграда и последние переходы состояния |
| `qa_run_probe` | Запуск одной разрешённой серверной проверки на отдельном QA-мире, возврат `job_id` |
| `qa_job_status` | Итог/статус проверки с длительностью и ссылками на приватные доказательства |
| `qa_read_events` | Ограниченная выборка событий попытки по ID и времени без целого сырого журнала |

Команды чтения удобно сделать первыми. Изменяющие мир проверки отделять от чтения; не выдавать инструменту
произвольный shell, сброс активного мира или все административные команды без различения назначения.
Для долгой операции возвращать ID и читать статус; неизвестный исход не повторять вслепую.
Сохранять единственного исполнителя для общей очереди. Метаданные возможностей не заменяют реальные проверки
мира, поставки, владельца операции и отсутствия пользовательского сеанса перед изменением площадки.

Возвращать компактные структурированные данные и короткую сводку, а не большие журналы или каждый кадр.
Такой формат поддерживается MCP-инструментами через `structuredContent` и `content`.
[Официальное руководство по серверу MCP](https://developers.openai.com/plugins/build/mcp-server).
Файлы мира, доступы, адреса и сырые события остаются приватными; подключение не требует публикации их в Git.

## Практическая рекомендация

Сначала закончить арену на текущих командах. Повторяемую отправку/ожидание можно вынести в один небольшой
CLI-контроллер и использовать его из shell; при необходимости MCP затем вызывает те же функции.
Не дублировать транспорт, правила backup, код тестов или управление вводом в двух независимых реализациях.
Если клиентский снимок нужен для конкретной ошибки, использовать существующий визуальный протокол;
MCP не отменяет свежесть наблюдения и остановку при потере фокуса.

После первого кандидата сравнить несколько одинаковых операций: число вызовов, время ожидания,
объём ответа и число ошибок до/после адаптера. Подключать MCP ради повторяемой экономии действий,
а не делать его обязательным предварительным этапом. В текущем запросе выполнена оценка пользы,
конфигурация приложений не менялась. Возможность загрузки собственного MCP в выбранном интерфейсе ещё не проверена.
