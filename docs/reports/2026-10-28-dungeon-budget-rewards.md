# Бюджетные награды охраняемых сундуков

Дата: 28 октября 2026 года. Этап: реализация и технические проверки отдельного механизма.
Это не игровая приёмка подземелья и не утверждённый баланс сборки.

## Реализация

`DungeonDepthPrototype` 0.2.0 заменяет один `SwordBronze` и модель возможностей PoV бюджетными группами.
[Код и воспроизведение](../../tools/dungeon-depth-prototype/README.md),
[общие правила](../../configs/dungeon-rewards.json).
PoV 5.3.6 и EpicLoot 0.15.3 сохранены, версия/SHA256 проверяются до установки адаптеров.
Сторонние архивы, DLL, исходные декомпиляции, журналы и миры остаются в `.local/`.

`Bind` сохраняет одного реального охранника: постоянный токен, исходный ZDO ID, prefab, позицию, уровень,
маску и строковые ID фактически назначенных модификаторов. Сохраняются также контекст комнаты,
seed, бюджет, сработавшие сочетания, снимок настроек и его хеш. Повторная привязка не меняет профиль;
использование той же охраны для другого сундука отклоняется. Смерть и расстояние от сундука не проверяются.
Перезапуск выявил перенумерацию native ZDO ID в `ZDO.Load` игры 1.0.20. Связи переведены на собственные
постоянные токены охраны и сундука, сохраняемые в ZDO. Исходный native ID остаётся только диагностикой.
После исправления используется схема 2 и отдельный новый мир; старый одноразовый fixture не мигрировался.

Бюджет равен `locationBonus + sum(weights) * product(matchedFactors)`.
Начальный ресурсный путь требует охрану без модификаторов и обнуляет также надбавку.
Веса едины для всех данжей; надбавка по умолчанию 0. Варианты +20/+40 не включены автоматически.
Нет зависимости от штатного количества наград PoV, чужого дропа, длительности боя и числа игроков.

Шкала качества: `12 / 24 / 48 / 72 / 96 / 108 / 120` для
`Common / Magic / Rare / Epic / Legendary / Mythic / Ancient`.
Между узлами — линейные вероятности соседних качеств, один бросок на всю группу.
Числа предварительные: шкала оставляет большинство одиночных свойств в области компенсации/раннего качества,
а сильные смешанные наборы дают высокую редкость без обязательного Ancient за число модификаторов.

При бюджете 120 выдаётся один Ancient, при 240 — три, при 360 — шесть.
Бюджет 432 даёт `6 Ancient + 4 Epic`; это проверочный случай, а не цель лесного баланса.
Размер следующей группы не меняет её шкалу. При нулевом остатке добавки нет;
при положительном остатке меньше 12 даются 50 монет один раз. Множителя ×3 у бонусов нет.
Полностью одинаковые вещи внутри группы отбрасываются с ограниченным повтором.

Сначала генерируется и сохраняется весь набор с текущими мировыми ключами.
Первое формирование привязано к RPC открытия/«забрать всё». Фоновые чтения `GetInventory` другими модами
не формируют закрытый бонус: это исправлено после проверки сохранённого отложенного сундука.
Затем вещи поступают в сундук
по мере освобождения места. Генератор выбирает основы из таблицы prefab сундука, использует resolver
ссылок и фильтр технологии EpicLoot. Строки материалов не превращаются в экипировку:
выбор повторяется условно среди подходящих исходных кандидатов. При нескольких исходных таблицах
сначала выбирается таблица равновероятно; внутри сохраняются её веса.
Это явное правило распределения нашего бонуса, не воспроизведение количества штатных бросков.

У EpicLoot 0.15.3 обнаружено два ограничения headless-пути:

- `CheckIfItemNeedsGate` сначала возвращает запрет при отсутствии `Player.m_localPlayer`, включая режим
  мировых ключей. В пределах только нашего синхронного выбора адаптер вызывает штатный `CheckGateBossKill`.
  Вне этого участка поведение фильтра не меняется. Разрешённые автором `ItemFallback` сохраняются.
- `PendingChestLoot.TryRoll` тоже требует локального игрока. Наш серверный бонус оставляет его pending-флаг
  для клиента; при наличии локального игрока вызывает штатный `TryRoll`. В headless-тесте отдельный fixture
  имитирует только этот триггер и вызывает настоящий `PendingChestLoot.Roll` с исходными таблицами.
  Это не проверка действий клиента и не изменение производственного генератора штатной добычи.

Статическая проверка выполнена по закреплённой DLL и
[исходному патчу контейнера EpicLoot](https://github.com/RandyKnapp/ValheimMods/blob/13e64c369d7ab230bed0f7033e7ffd7acc75bc43/EpicLoot/src/GamePatches/Container_Patch.cs).
Новый босс не пересоздаёт готовый набор. Unity RNG сохраняется и восстанавливается вокруг собственных операций.
Штатный случайный бросок, обычные предметы и награды/опыт PoV продолжают существовать отдельно.

Выдача использует очередь и журнал снимков inventory «до/после». Пробное добавление выполняется на копии:
это предотвращает потерю части стопки монет при `AddItem == false`.
При точном совпадении с одним из снимков незавершённая запись завершается однократно.
При неизвестном содержимом журнал не затирает его; требуется диагностика.
Журнал сравнивает исходные байты ZDO. Найдено дополнительное усечение прочности на 0,01 при vanilla
Save/Load: механизм больше не использует такие повторные загрузки для копирования обычного содержимого.
EpicLoot при первом `Clone` обычной вещи добавляет пустой служебный `MagicItemComponent`; тест отказа
сравнивает сами предметы, количество, прочность, магические свойства и позиции. Пустая метаинформация
не считается потерей предмета; количество монет проверяется отдельно.
В открытом интерфейсе inventory не заменяется; очередь продолжается после закрытия/нового открытия.

## Предварительные веса лесной охраны

В первой таблице явно разрешены следующие десять ID. Другим свойствам не приписывается условная цена:
привязка неподдержанного набора отказывает до создания бонуса. В таблице нет скрытой наценки
за вид врага, звёзды или биом. Эти параметры важны при оценке воздействия, но не меняют глобальный вес.

Для сравнения использован ориентир `40 * ln(relativeThreat)` с конечными сценарными поправками.
Это способ расположить свойства на одной шкале, а не измеренная вероятность победы или цена вещи.
Веса контроля и восстановления требуют более грубых допущений, чем физическая защита.

| ID PoV | Очки | Основание и предел интерпретации |
| --- | ---: | --- |
| `swift` | 6 | Скорость ×1,4; условный рост доли контакта ×1,16 даёт `40 ln(1,16) ≈ 5,94` |
| `furious` | 5 | Анимация ×1,18; при 70% анимации в цикле `1/(0,3+0,7/1,18) ≈ 1,12`, около 4,5 очка |
| `armored` | 14 | Физический вход ×0,7: `40 ln(1/0,7) ≈ 14,27`; замедление ×0,85 не повышает цену |
| `warded` | 4 | Щит — перенос 40% HP, не дополнительные 40%; небольшой резерв за особенности щита/восстановление |
| `hardy` | 7 | 2% HP/с после 4 с без удара; условная пауза 14 с возвращает 20% HP: `40 ln(1,2) ≈ 7,29` |
| `greedy` | 8 | Лечение 20% исходного боевого урона; сценарный резерв около 20% HP, округление вверх |
| `keen` | 3 | Обзор ×2 и привлечение соседей; малая конечная оценка поддержки, без оплаты соседей как новой охраны |
| `steadfast` | 7 | Входящее оглушение ×0,34; резерв около ×1,2 за потерю окон контроля, не утроение HP |
| `piercing` | 22 | Игнорирует 22 пункта брони и долю 0,12 сопротивления; большой, но зависимый от экипировки эффект |
| `unbreakable` | 26 | Предел удара — 20% максимального HP; замеры выявили сильную защиту от больших ударов |

Для `warded`, `keen`, `steadfast`, `piercing` и `unbreakable` конечные веса содержат экспертную поправку.
Они не выведены полностью из измеренного DPS. Особенно `unbreakable` может быть существенно недооценён
в узком сценарии высокой брони/малого HP; присваивать бесконечный бюджет такому сочетанию нельзя.
Необязательные глубокие ветви пока не имеют подтверждённой боевой проходимости.
`FuriousSpeed` не приравнивается к постоянному DPS: AI и паузы атак ещё не измерены.

Автоматические удары прошли через настоящий `Character.RPC_Damage`, без игрока и без имитации победы.
Для свежих Skeleton и Greydwarf с уровнем 1 результаты совпали; максимальное HP контроля — 48.
Серия содержит 30 случаев: два prefab, три входных slash-удара и пять наборов.

| Исходный slash | Без свойств: потеря HP | Armored | Unbreakable | Armored + Unbreakable |
| ---: | ---: | ---: | ---: | ---: |
| 8 | 0 | 5,6 | 0 | 5,6 |
| 16 | 8 | 3,2 | 1,6 | 1,6 |
| 38,4 | 30,4 | 18,88 | 1,6 | 1,6 |

Это результат всего установленного конвейера PoV/игры, не только умножения на 0,7.
Для удара 8 обнаружена немонотонность: Armored получил больше урона контроля. Причина ещё не установлена;
её нужно разобрать перед игровой калибровкой, не подгоняя ожидаемый результат теста.
Для двух больших ударов предел Unbreakable доминировал, а добавление Armored не усилило защиту.
У Warded записана отдельно потеря HP, которая не равна полному расходу HP + щита.
Эти измерения обосновывают осторожность и разный порядок весов, но не доказывают их точную величину.

Сочетания тоже глобальные и оплачивают только небольшой дополнительный эффект:

| Правило | Коэффициент | Основание |
| --- | ---: | --- |
| `armored + greedy` | 1,05 | Защита продлевает пользу лечения; `(1/0,7 * 1,2)/(1/0,7 + 0,2) ≈ 1,053` |
| `furious + greedy` | 1,03 | Частые удары усиливают лечение; верхний ориентир `(1,18 * 1,2)/(1,18+0,2) ≈ 1,026` |
| `furious + piercing` | 1,04 | Небольшая доплата за частоту пробивающих ударов; реальная частота неизвестна |

Коэффициенты перемножаются при совпадении всех перечисленных ID; порядок ID ничего не меняет.
Полный прирост защиты/урона не умножается на бюджет повторно. Для `armored + unbreakable` отдельной надбавки нет:
при сильном ударе общий предел уже обрезает урон, и нельзя автоматически оплачивать оба снижения как независимые.

[Прогноз по конфигу плагина](../../manifests/dungeon-runtime-reward-forecast-20261028.json)
перебирает все 1024 поднабора. Без надбавки максимум десяти свойств — 114,72552 очка:
одна группа, около 56,05% Ancient и 43,95% Mythic, без гарантированного завершения шкалы.
Для пяти свойств диапазон 25–84,357, для восьми — 58,401–106,8522.
Это диапазоны возможных наборов, а не частоты их появления и не целевой темп наград.
Число охраняемых сундуков, разборка, MWL ×2 и общая экономика пока не откалиброваны.

## Подтверждённые проверки

Окончательная серия выполнена 28 октября, 16:25–16:38 по Asia/Yekaterinburg.
[Машинная сводка](../../manifests/dungeon-reward-results-20261028.json) содержит UTC, SHA256 кода/DLL,
идентичность поставки, результаты и измерения. Неуспешные отладочные прогоны не включены в число успешных.
Во всех трёх окончательных фазах использована одна DLL 0.2.0 без пересборки между загрузками.

| Проверка | Результат и область подтверждения |
| --- | --- |
| Чистый .NET | 11 397 утверждений: веса, все 1024 поднабора, шкалы/группы, ноль/монеты, журнал и граф комнат |
| Репозиторий | `make check`: 26 Python-тестов, compileall, shellcheck, `git diff --check` |
| `create` | 1267 утверждений на настоящих объектах Valheim, PoV и EpicLoot |
| `resume` | 28 утверждений после сохранения и перезапуска; очередь переполнения завершена |
| `verify` | 18 утверждений после загрузки восстановленного backup; данные совпали повторно |
| Технология | 960 предметов: два источника × четыре стадии ключей × 120 генераций |
| Механики охраны | 30 вызовов настоящего `Character.RPC_Damage`; ограничения трактовки указаны выше |

Проверены 21 бюджетная граница, все семь качеств, группы одного цвета с отдельно созданными предметами,
сохранение завершённых групп и пример `6 Ancient + 4 Epic`. Модификатор обычных ресурсов сервера — ×3;
компенсация осталась ровно 50, количество бонусных вещей соответствовало плану.
Дополнительный случай фиксирует десять фактических ID охраны: живого охранника переместили,
сундук выдал прежнюю награду. Повторная привязка не изменила бюджет, назначение второго сундука отклонено.

Настоящий `RPC_RequestOpen` вызван с серверным сетевым отправителем, без игрока и графического интерфейса.
Он сформировал одну награду, повторный вызов не добавил копий. Предварительное фоновое чтение inventory
награду не формировало. Это проверка серверной точки входа, не визуальное открытие сундука клиентом.

Для независимости штатного дропа выполнена матрица `бюджет 0/120 × native rate 0/4`:
штатных магических предметов получилось 0/1, нашей добавки — соответственно 0/1 по бюджету.
При одном seed готовые бонусы совпали независимо от штатного результата. Проверены сохранность обычного
содержимого, независимость Unity RNG и поздний штатный бросок после нашей выдачи.
Штатный триггер в этих случаях имитирован headless-fixture, как описано выше; исходный конфиг 0,7 восстановлен.
PoV не перехватывается в точках смерти/опыта/выдачи наград; его полная боевая экономика здесь не проверялась.

Фильтр технологии прошёл все 960 выборов, включая штатные `ItemFallback` без ключей.
До соответствующих ключей закрытые бронзовые/железные основы не появились.
После Старейшины в выборке появилась бронза; после Массы костей в болотном источнике появилось железо.
Лесной источник после этого не обязан выдавать железо: действует также его собственная таблица.
Новый ключ босса не изменил уже сформированные вещи. Сундук, оставшийся неоткрытым до перезапуска,
сформировал набор с ключами, действовавшими именно в момент первой генерации.

Переполнение проверено на настоящем `Inventory`: полный сундук сохранил очередь, после освобождения двух
ячеек выдал 2 из 10 записей, после перезапуска и постепенного извлечения содержимого — все 10.
Сумма оставшихся и извлечённых обычных/бонусных вещей совпала с ожидаемой, повторных выдач не было.
Отдельный случай с почти полной стопкой монет подтвердил отказ без частичной потери и последующую выдачу 50.
Два управляемых исключения — после записи журнала и после записи inventory — завершились однократным
восстановлением. Это инъекции исключений в процессе, не испытание отключения питания или `SIGKILL`.

Три постоянных сценария — готовая награда, частичная очередь и ещё не сформированный бонус — пережили
сохранение/перезапуск. Сверены исходные байты inventory, сохранённое состояние награды и токены охраны.
После второй штатной остановки backup всего состояния и конфигов, включая внешние данные EpicLoot,
извлечён в отдельный каталог: SHA256 всех 115 файлов совпали. Эта копия прошла фазу `verify` той же DLL.
Это восстановление состояния; откат версии мода и подключение клиента при восстановлении не проверялись.

Поставка: Valheim `l-1.0.20`, build `25909431`, фактические manifests `1006:4559160656493359681`
и `896661:4001404753685205688`. Повторно сверены семь компонентов
[lock](../../manifests/dungeon-prototype.lock.json), конфиг наград и контрольные файлы игры.
Стенд: 6 vCPU, 7946 МиБ RAM; перед заключительной загрузкой свободно около 6,0 ГиБ RAM и 145 ГиБ диска.
Лимиты каждого процесса: 4 ГиБ RAM, 200% CPU, 900 секунд; максимальный учтённый пик — около 2,04 ГиБ.
Это измерение отдельного сервера без игроков, не оценка вместимости целевой машины.
После каждой фазы подтверждено `World save (5/5) done`; сервер остановлен, тестовые порты освобождены.
Исходная поставка, предыдущие состояния и согласованные backup сохранены приватно.

## Границы этапа

Геометрия не менялась. `RoomRewardContext` и `Bind` подготовлены для адаптера комнат лесного склепа
по [плану генерации](../dungeon-generation.md). Самостоятельного поиска охраны по расстоянию нет.
Серверные объекты создавались программно в отдельном мире. Это подтверждает API и сохранение при успешных
сценариях, но не естественную генерацию наград в данже, пользовательский интерфейс и игровой проход.

Доступен один известный Windows-стенд, во время проверки игровой процесс отсутствовал.
Второй клиент не подготовлен; передача владельца между двумя настоящими клиентами не проверена.
Клиентская приёмка нового плагина, совместная работа с полным основным кандидатом и нагрузка остаются впереди.
Разрушение сундука с невыданной очередью и передача большого ZDO у технического предела 256 предметов
не испытаны. Журнал защищает проверенные переходы; неизвестный конфликт требует диагностики.
Веса предварительные, немонотонность малого удара по Armored остаётся открытой боевой проблемой.
Основной клиент и существующий мир не изменялись. Новых зависимостей и обновлений игры нет.
